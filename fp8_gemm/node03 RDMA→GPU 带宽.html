node03 RDMA→GPU 带宽

node03 · Mooncake TE · 单 NIC loopback · 1 GiB × 20 次 · GB/s

RDMA 写进 GPU 有多快

NIC 往 GPU 写数据的速度，取决于 NIC 和 GPU 在 PCIe 上隔多远。换成 dmabuf 注册也不会变快。线上 prefill 每张卡只跑到约 13 GB/s。去掉本机 store segment、只读远端的 store 后，每卡回到约 49，问题出在本机 store 的读取走了离 GPU 远的 NIC。

已测

PCIe 位置决定速度

NIC 和 GPU 在同一个或相邻 root 下约 49，跨 root 约 18，跨 socket 约 13。写主存在任何位置都是约 48。

已测

dmabuf 没有收益

写 GPU 时两种注册方式的带宽一样，GPU→host 方向 dmabuf 还更慢。ViT encoder 的 graph 不用关。

已验证

线上慢在本机读

每卡 rx 约 13，最后一个 stage 约 20，正好落在跨 socket 和跨 root 两档。去掉本机 store segment、只读远端 node03 的 store 后，每卡回到约 49。

这个测试量的是什么

一张 NIC 自己发给自己（loopback），数据不出网口。所以测出来的是 NIC 到主存、NIC 到显存这两段 PCIe 路径的速度，跟网络无关。测试 pod 拿到的 GPU 是 0000:15:00.0，和 ionic_3（19:00.0）挂在同一个 root complex 下。下文说的「远」「近」都是相对这块 GPU。

host→host
主存写主存。这是基准，看 NIC 本身能跑多快。
host→GPU 写
RDMA write。NIC 把数据直接 DMA 进显存（GPUDirect RDMA）。
GPU→host 写
NIC 从显存读出数据，再写进主存。
host→GPU 读
RDMA read。数据同样落进显存。

位置决定写 GPU 的速度

NIC 写主存是 PCIe 设备最常走的路径，CPU 对它做了充分优化，所以每张 NIC 都能跑到约 48。NIC 写显存是两个 PCIe 设备之间的点对点传输（P2P）。同一个 root 下几乎直达；跨 root 要经过 CPU 的 IO die 转发；跨 socket 还要再过一次 socket 间互联。转发得越远，速度越慢。

dmabuf 没有收益

显存要先注册给 NIC 才能做 RDMA，有两种方式。MOONCAKE_DISABLE_HIP_DMABUF=1 用旧的 peer-memory 方式，=0 用 Linux 的 dma-buf。上面的数据都是 =1。换成 dma-buf 后，写 GPU 的带宽几乎一样，说明瓶颈在 PCIe 路径上，跟注册方式无关。

对照线上 prefill

prefill 的 4 个 rank 在 NIXL 这边都是本地配对。启动日志里的 vllm_net_devices 显示每块 GPU 都配了同 root 的 NIC（PCI distance 8），Mooncake 用的也是这 4 条 rail。照理说，远端 store 读来的数据经本地 NIC 写进 GPU，应该能跑到约 49。

  • GPU 15:00→ ionic_3 · 19:00
  • GPU f5:00→ ionic_4 · f9:00
  • GPU e5:00→ ionic_6 · e9:00

本机读走错了 NIC 已验证

store 的数据一部分在远端节点，一部分在 prefill 本机的主存里（本机 store segment）。远端那部分从网络进来，经 GPU 本地的 NIC 写进显存，路径正确。本机那部分不经过网口，在 NIC 内部 loopback。从速度看，Mooncake 是按 store segment 所在的 NUMA 挑的 NIC，没考虑目的 GPU 在哪，写显存这一段就成了跨 root 或跨 socket 的 P2P。一次 get 要等所有分片都返回，本机这部分一慢，整个 get 都被拖住。

验证结果　prefill 所在节点不放 store segment、只用远端 node03 的 store 后，每卡吞吐从约 13 回到约 49。慢的就是本机这部分读取。具体落在哪张 NIC 还没直接看到，但 13 和 18 这两档速度说明它走的是离 GPU 远的 NIC。

现状和修法一都跨了 NUMA，区别在跨的是哪一段。现状是在 P2P 写显存那一段跨，测试里跨 socket 只有约 13。修法一改成在 NIC 读主存那一段跨，这是设备访问内存的常规路径，CPU 对它优化得很好；写显存那一段回到同 root，约 49。修法二两段都不跨，路径最短，但要求每个 rank 要读的数据正好放在它自己 NUMA 的 segment 里。

修法一还有一点要确认。测试没有单独测过「NIC 读另一个 NUMA 的主存」这种组合。如果测试 pod 的 host buffer 分配在 socket 0，那 ionic_4–7 的 host→host 约 48 已经说明跨 socket 读写主存能跑满。可以查一下 buffer 当时在哪个 NUMA，或者用 numactl --membind 把 buffer 绑到另一个 NUMA，再经 ionic_3 写 GPU 15:00 补测一次。

下一步

  1. 验证本机读是瓶颈（已完成）

    • prefill 所在节点不放 store segment，只用远端 node03 的 store：每卡吞吐从约 13 回到约 49。
    • 还可以在 Mooncake TE 里打开 per-device 统计，直接看到本机读落在哪张 NIC 上，修完后用它做前后对比。

  2. 修本机读的路径

    • 临时办法：prefill 节点先不放 store segment（已测约 49）。代价是 store 少了这台机器的容量，所有读取都要过网络。
    • 修法一：同机读也走 GPU 本地 NIC，选 NIC 时以目的 GPU 为准（destination affinity）。前提是跨 NUMA 读主存能跑满，先补测。
    • 修法二：让 store segment 按 GPU 本地 NIC 做 NUMA / rail 对齐。前提是能控制每个 rank 的数据落在哪个 segment。

补充意见

下面几点不在原始结论里，是读完数据后的补充。

  • 本机读可以完全不经过 NIC。store segment 和 GPU 在同一台机器上时，用 hipMemcpy 做 H2D 拷贝，由 GPU 自己的 DMA 引擎读主存。这走的是设备读主存的常规路径，不受 P2P 限制。可以查一下 Mooncake 对同机读有没有这样的本地路径。
  • dma-buf 在 GPU→host 方向更慢。如果 put（GPU 写回 store）也走 RDMA，保持 MOONCAKE_DISABLE_HIP_DMABUF=1 对 put 也更好。

术语

Root complex
CPU 上的 PCIe 根端口。挂在同一个 root 下的设备之间路径最短。
P2P
两个 PCIe 设备直接互传，不经过主存。NIC 写显存就是 P2P。
GPUDirect RDMA
NIC 直接把数据 DMA 进显存，不在主存中转。
peer-mem / dma-buf
把显存注册给 NIC 的两种方式，由 MOONCAKE_DISABLE_HIP_DMABUF 切换。
Loopback
NIC 发给自己，数据不出网口。本机 store 的读取就是这种情况。
Rail
一组固定配对的 GPU 和 NIC，例如 GPU 15:00 和 ionic_3。
Store segment
某台机器贡献给 Mooncake store 的一块主存。
NUMA / socket
每个 CPU socket 有自己就近的内存和 PCIe 设备，跨 socket 访问要过 xGMI。
